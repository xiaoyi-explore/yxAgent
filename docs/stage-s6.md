# S6 —— 上下文管理、预算与压缩（里程碑 M4 之前最后一课）

> 上游计划：`new-agent-stages-v2.md` 的 S6 节。本文件记录**为什么这么设计、替代方案、踩了什么坑**。

## 1. 一句话

**上下文是有限的，而对话是无限的。** S6 让 core 在历史撑爆之前自己动手：
先裁工具结果、再把最老的几轮折叠成摘要、实在不行连"证据"一起压。
前端**一个字都不用改**——它只多看到一个新事件 `context.compacted`。

交付物：`src/core/context.{hpp,cpp}`（`ContextManager`）、`--max-context-tokens` / `--keep-recent-turns`、
`context.compacted` 事件、`tests/context_test.cpp`（算法）+ `tests/test_s6.py`（接线）。

---

## 2. 为什么压缩不只是省钱

**context rot**（Anthropic 的观察）：上下文越长，模型对**早期事实**的召回越差。
所以"压缩"的第一目的是**保效果**，省 token 只是副产品。这解释了为什么压缩策略要
"保最近、摘要最早"——而不是"随手删掉前一半"。

---

## 3. 六个决策

### 决策 1：token 用**估算**，但账本用 `usage`

没有 tokenizer（引一个就是几 MB 依赖），所以估算 = `字节/4 + 每条 8 字节开销`。

- 英文 ≈ 4 字节/token，几乎准确；
- 中文一个字 3 字节 ≈ 0.75 token，会**低估**——所以默认预算 32000 而不是 64000，留一半余量。

**估算只用来决定"要不要压"；真正的账本是响应里的 `usage`。** 两者用途不同，别混：
估算可以保守，账本必须诚实（对端不给 `usage` 时显示"未知"，不许显示 0）。

### 决策 2：三级压缩，按"便宜 → 贵"排序

| 级别 | 做什么 | 代价 |
|---|---|---|
| **1. 工具结果裁剪** | 老的非检索类工具结果截断到 2KB | 不丢消息，只砍体积 |
| **2. 摘要压缩** | 估算超过预算的 50% 时，把最老的**整轮**折叠成一条抽取式摘要 | 丢原文、留要点 |
| **3. 兜底** | 压完还爆（比如一轮 `read_file` 就吃掉预算），把**所有**工具结果继续减半，直到进预算或到 256 字节地板 | 连证据一起压 |

顺序不能反：先做免费的，再做贵的。第 1 级每轮都会跑（不进阈值也跑），
所以"老的工具输出"不会一直躺在历史里烧钱。

**阈值 50%**：等快满了再压，你会先被"一次多轮工具调用"顶爆——压缩本身需要空间。

### 决策 3：摘要是**抽取式**，不调模型

| 方案 | 评价 |
|---|---|
| A. 让模型写摘要（多一次请求） | 效果最好，但要 key、要花钱、**测试不可控**（摘要内容没法断言） |
| B. **抽取式（采用）** | 把被折叠轮次的 user 内容 + 助手首句拼成 "`- 用户：… → 助手：…`"，纯本地、确定性、可测 |

抽取式的诚实说法：**它不是"理解之后的总结"，是"挑几句留下"。** 好处是永远不会编造，
坏处是长答案的细节会丢。真要做模型摘要，那是 S6.1（登记在 §5）。

### 决策 4：**轮级豁免**——含检索类工具结果的轮，整轮不折叠

"检索类工具结果永不压缩"（Gemini CLI 的实测值）不能按**消息**实现，只能按**轮**实现。

原因：`tool` 消息前面必须有 `assistant(tool_calls)`，否则请求直接被任何 OpenAI 兼容端点拒绝。
如果你只保留那条 tool 结果、却把它上面的 assistant 折叠掉，历史就出现**孤儿 tool 消息** —— 400。

所以：**要么整轮留，要么整轮折**。检索类（`read_file`）的轮 = 整轮留。

`is_retrieval()` 是一张显式的表：**新加工具时要在这里表态**——它算不算"证据"。

### 决策 5：硬保证——压缩不许把历史**变大**

短对话里，摘要的固定开销（"`[压缩] 更早的 N 轮已折叠…`" + 每行的前缀）可能**超过原文**。
第一版就撞上了：压完 149 → 149（甚至更大），因为 4 条短消息被写成了 4 行摘要。

所以重建之后要**量一下**：`if (estimate(rebuilt) >= estimate(history)) 放弃这一步`。
这条保证让"压缩"在任何情况下都不会变成"膨胀"，也让短对话永远不触发——那是**正确行为**，
不是 bug。（这也是为什么测试里的消息必须写得像真的。）

### 决策 6：`history_mark` 必须跟着压缩往下挪

失败回滚用的是"进 turn 前记一个水位线，出错 `resize(mark)`"。压缩会让 `history_` **变短**——
如果水位线还停在原来的高度，`resize(mark)` 会把历史**撑大**（补一堆空消息）。

所以压缩成功之后：`if (history_mark > history_.size()) history_mark = history_.size();`

这是 S6 唯一改动 S3a 老代码的地方，也是**最容易漏**的地方：它只在
"压缩发生在工具循环中途，然后又失败"时才暴露。

## 4. 协议：只多一个事件

```json
{"type":"event","seq":7,"name":"context.compacted","payload":{
  "turn_id":"t3","step":1,"budget":32000,
  "before_tokens":18400,"after_tokens":9100,
  "dropped_messages":12,"summarized_turns":3,"truncated_tool_results":2}}
```

- 位置：**在任何 `assistant.delta` 之前**（它发生在"模型还没被调用"的时候）。
- `response` 仍是本轮最后一帧（不变量 1 不变）。
- **compress 之后前端什么都看不见**：它收到的 delta 和以前一模一样。
  这个事件只是"知情权"，不是"控制权"。

## 5. 已知限制（刻意不做）

| 限制 | 为什么现在不修 |
|---|---|
| 不做**模型摘要**（LLM summarization） | 多一次请求、要 key、摘要内容不可断言。抽取式已经能通过"压缩后仍能答对早期事实"的验收 |
| 不做**工具结果的结构化裁剪**（比如只保留 JSON 的前 N 个字段） | 那要认识每个工具的语义，属于工具层的活 |
| 不按"消息重要性"排序折叠 | 没有可靠的重要性信号；按时间折叠是最不容易错的 |
| 估算不含 tools schema / system 的额外膨胀 | 低估方向是安全的（宁可早压） |
| 不持久化摘要 | 落盘是 S7 的事；S7 要处理"恢复时摘要还算不算数" |

## 6. 踩到的坑

1. **摘要套娃。** 旧摘要本身是 `role:"user"` 的消息，第一版把它当普通一轮又折叠了一次，
   结果是 `[压缩] … [压缩] … [压缩] …` 递归变长，token 反而上升。
   修法：识别摘要（前缀 `[压缩]`），只搬运它的**正文**（`carry`），不重新折叠。
2. **兜底不可达。** 所有老轮都是检索类时，`turns == 0` 提前返回——而第三级兜底写在
   "摘要成功之后"，于是永远走不到，请求照样被撑爆。
   修法：把"兜底 + 收尾"收成唯一的出口 `finish()`，所有 return 都走它。
   **同一件事只能有一个出口**——这是 S2 就立过的规矩，这里又踩了一次。
3. **单元测试的 `check(name, cond, detail)` 里，`detail` 是无条件求值的。**
   `h[2].content.substr(2048, 60)` 在条件为真时也会执行 → 越界 → `terminate`。
   教训：断言辅助函数的**所有参数都要被求值**，副作用/越界要放在外面算好再传。
4. **短消息压不动是正确行为。** 第一版测试用"问题0""第1句"这种五六个字的对话，
   压缩永远触发不了（被决策 5 的硬保证拦住）。测试里的消息必须写成真实长度（几百字节），
   否则你测的是"摘要开销"而不是"压缩收益"。
