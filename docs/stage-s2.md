# S2 阶段设计记录 —— 管道里跑通假对话流

> 每阶段一份：**为什么这么设计、替代方案是什么、踩了什么坑**。
> 本阶段新增概念只有 3 个：**事件流**、**抓包（log-raw）**、**同进程直连（embedded）**。

---

## 1. 本阶段目标

让 core 到 cli 这条管道第一次**连续地**流动：一个请求产生一串事件，最后才结算响应。
内容仍然是假的（确定性假模型），因为真正的目的是**把管道本身验完**——S3 接真模型时，
"卡住了"就只剩 HTTP/SSE 一个嫌疑犯。这就是"一次只调一个未知数"。

交付物：`demo.chat` + `assistant.delta`（事件流）、`--log-raw`（抓包）、`--embedded`（同进程直连）。

---

## 2. 四个关键决策

### 决策 1：response 放在**流结束后**，而不是先回一个 ack

| 方案 | 形状 | 问题 |
|---|---|---|
| A. 先 ack 再流（未采用） | response 先回 `{accepted}`，再推事件，最后需要一个**终止事件** | 要多发明一个"流结束"消息；而真实 API 的结束信号本来就在流内部（`finish_reason` / `[DONE]`） |
| B. 流完再结算（**采用**） | 请求 → N 个事件 → 恰好 1 个 response | response 迟到，但语义最干净：**它就是本轮结束** |

选 B 还有一个更硬的理由：**真实 LLM 也是流完才知道结果**（要在 `finish_reason` 之后才能定 usage）。
现在按 B 定协议，S3 接真 Provider 时**帧的形状完全不用改**——协议文档里 S2 那一节可以直接被 S3 复用。

代价与它带来的纪律：响应会迟到，所以 §5"请求不能悬空"必须理解成"**最终**必有响应"，
而不是"立刻有响应"；cli 侧也必须学会"等响应的时候顺手处理事件"（见 `PipeSession::call` 的循环）。
### 决策 2：`--embedded` 用**回调**实现，不用线程

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 线程 + 内存队列模拟管道（未采用） | 起一个线程跑 core，用队列收发 | 复刻了进程行为，也把并发 bug 一起复刻进来——调试工具自己成了新的 bug 源 |
| B. 把"写出到管道"换成"调用函数"（**采用**） | 引擎暴露 `handle_request(req, sink)`，embedded 时 sink 就是 cli 的渲染函数 | **零线程、零队列**；同步回调，事件天然有序 |

这带来一个结构性收益：`CoreEngine` 从 `main.cpp` 里独立出来，**它不知道自己在哪个进程里**。
对应 Codex 的 `InProcessAppServerClient` / `RemoteAppServerClient`：同一个接口，两种传输。

**代价（必须登记）**：`agent-cli` 因此链接了 `agent_core_lib`。这违反"前端不认识 core 内部"的精神，
所以写进了 `docs/responsibilities.md` 的已登记例外，并明确：S3 接入 HTTP 时，
必须把 httplib 挡在 `agent_core_lib` 之外，否则例外会变成侵蚀。

### 决策 3：假模型按 **UTF-8 码点**吐字，不按字节

按字节切最省事，但一个汉字是 3 字节，切出来就是"半个汉字"——前端画出来是乱码。
本阶段手写 `split_utf8_codepoints()`（约 20 行：看首字节定长度、越界就退回单字节），
顺带处理两个真实世界的边界情况：**非法首字节**和**被截断的序列**都不能让它死循环。

这是 S3 那条 fixture（chunk 切在 UTF-8 码点中间）的预演：流式解析里，"边界不在你以为的地方"是常态。

### 决策 4：抓包（`--log-raw`）放在 core，格式是"方向前缀 + 原样一帧"

```
--> {"id":"h1","method":"hello","params":{},"type":"request"}
<-- {"name":"hello","payload":{},"seq":1,"type":"event"}
```

- 放 core 而不是 cli：core 看到的是**全部**帧（含自己主动发的），而且 embedded 模式下 cli 根本没有"线路"可抓。
- 用 `-->` / `<--` 前缀而不是嵌套 JSON：NDJSON 天生可读，`grep -- "-->"` 就能只看请求方向；
  去掉前缀后每行仍是合法帧（测试就是这么验的）。
- **每帧 flush**：抓包文件的第一用途是"崩了之后看最后一句"，攒缓冲会让它失去意义。
- **两种模式的抓包必须逐行一致**：`event hello` 由 `CoreEngine::greet()` 统一发出，
  管道模式在 `run()` 开头调，embedded 在握手时调。于是 `diff pipe.log emb.log`（pid 除外）= 空，
  **diff 抓包就等于 diff 行为**——这才是 `--embedded` 作为调试利器的完整形态。

## 3. 踩到的坑（DoD 第 6 条）

1. **日志差点被记两遍**：`run()` 里的输出通道和 `handle_request()` 里的 `emit` 都想记日志。
   修法：规定"请求帧与它产生的所有帧"由 `handle_request` 负责记，`run()` 只记自己产生的帧
   （hello、PARSE_ERROR、INVALID_ENVELOPE）。**同一件事必须只有一个负责人**，否则日志会骗人。
2. **embedded 少记了一帧**：第一版里 `event hello` 只在 `run()` 里发，embedded 直接问 `hello_payload()`，
   于是它的抓包少一行、握手还走了另一条代码路径。修法即上面那条 `greet()`——
   **同一件事只能有一条实现路径**，否则"两种模式应该等价"这句话就只是口号。
3. **按字节切字会乱码**：这类 bug 不会崩，只会"看起来不对"，
   所以测试里直接把"每个 delta 恰好一个码点"写成断言，让它在 CI 里当场现形。

## 4. 已知限制（刻意不修）

| 限制 | 为什么现在不修 |
|---|---|
| `shutdown` 后 `waitpid` 没有超时 | core 若卡住，cli 会一直等。S5 引入取消语义时一起做超时与强杀 |
| embedded 模式没有真并发 | 它本来就是降级调试通道，同步回调够用 |
| `--log-raw` 每次启动**截断**旧文件 | 行为可预测优先；"追加保留历史"是 S7 transcript 的事 |
| 假模型的回复是模板拼的 | 它只需要确定性 + 可测，不需要像人 |

---

## 5. 留给 S3 的接口（不要改这些形状）

1. `demo.chat` 的**帧形状**：请求 `{text}`；事件 `assistant.delta{turn_id,text}`；响应 `{turn_id,text,stop_reason}`。
2. `CoreEngine::handle_request` 的签名 `(req, sink)` —— S3 只需在内部把 `demo_reply()` 换成 `Provider::stream()`。
3. `--log-raw` 的格式：S3 抓真 SSE 时会多出原始 SSE 事件这一层调试产物（transcript），但**帧日志格式不变**。
